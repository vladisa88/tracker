# 05: Подключение Telegram-бота

**What to build:** Владелец открывает бота из приложения, отправляет `/start`, получает проверочное сообщение и видит состояние подключения. Подключение напоминаний является отдельным действием после входа через Telegram. Использовать согласованную спецификацию и проверенные заметки о Telegram.

**Blocked by:** 01 — Вход владельца и запуск приложения.

**Status:** ready-for-agent

**User stories:** 21, 22, 31, 32.

- [x] Закрытая операция получения состояния подключения возвращает понятный статус и ссылку открытия бота; токены и секреты не выдаются.
- [x] Отдельный Go-процесс получает обновления через long polling. `/start` принимается только от числового ID владельца и только в private-чате; сохраняется chat_id, а не username.
- [x] Посторонние аккаунты и групповые сообщения не меняют получателя и не получают финансовые данные. Вход на сайт не переводит бота в подключённое состояние автоматически.
- [x] Подключение и позиция получения обновлений сохраняются в PostgreSQL. Перезапуск продолжает обработку, не повторяя обычные уже обработанные побочные действия.
- [x] В ответ на подключение отправляется проверочное сообщение. Повторный явный `/start` владельца может повторно проверить связь. Успех и постоянная ошибка проверки отражаются различимыми состояниями.
- [x] Русский интерфейс показывает отсутствие подключения, готовность и ошибку доступности; содержит понятную последовательность подключения и не мешает остальным функциям приложения.
- [x] Процесс запускается в локальном Docker Compose, проверяет конфигурацию и использует внешний адаптер Telegram; тестовая реализация не открывает обход production-проверок.
- [x] Проверки с PostgreSQL и управляемым Telegram подтверждают правильного получателя, запрет чужих/групповых обновлений, проверочное сообщение, ошибку и возобновление после перезапуска. Браузерная проверка подтверждает состояния подключения. Записаны результаты и завершение задачи.


## Implementation

**Состояние реализации: завершена.** Проверено 16 октября 2026 года. Triage-статус выше сохранён; он не обозначает завершение.

Коммиты реализации: `98cb3ad`, исправление после ревью: `6d8d639`. Подключение не зависит от входа на сайт. Добавлены защищённый `GET /api/telegram/connection`, отдельный Go-процесс `/bot`, PostgreSQL-состояние и курсор обновлений, long polling через внешний Telegram-адаптер и русская панель подключения. Доступные состояния: disconnected, checking, connected, error. Проверяется числовой отправитель и private-чат, сохраняется chat_id. После постоянной ошибки повторная проверка требует нового `/start`; временная ошибка повторяется с задержкой. Постоянная ошибка polling также сохраняется для интерфейса.

Миграция Telegram имеет независимый версионируемый журнал и использует общую блокировку запуска. Это позволило сохранить параллельную реализацию подписок без смешивания её изменений с задачей 05. Два процесса сериализуют цикл блокировкой строки подключения. Сообщение и курсор фиксируются одной транзакцией; авария между внешней отправкой и commit допускает согласованный редкий дубль.

Настройка и команды: [инструкция Telegram](../../../docs/telegram-bot.md), [README](../../../README.md). Нужны TELEGRAM_BOT_USERNAME и TELEGRAM_BOT_TOKEN отдельно от Login credentials. В production нет тестовых маршрутов, провайдера или переменной обхода проверки владельца.

## Validation

Проверки использовали отдельную PostgreSQL 17 в Compose-проекте `tracking-bot-check` на порту 55435, чтобы не мешать параллельной задаче. DSN: `postgres://tracking:test-only@127.0.0.1:55435/tracking_test?sslmode=disable`. Полный финальный прогон после исправления ревью успешен:

- Backend: `go vet ./...` и `TEST_DATABASE_URL=... go test -race ./... -count=1` — проходят все пакеты, включая существующие проверки входа и подписок.
- Целевые тесты: `TEST_DATABASE_URL=... go test ./internal/app -run '^TestBot' -race -count=1` — проходят. Наблюдаемое поведение проверяется через аутентифицированный HTTP и контролируемый внешний Telegram transport при настоящей базе: отдельность входа, правильный chat_id, запрет чужих/group/supergroup обновлений, проверочное сообщение, новые экземпляры API и worker/новые подключения к базе, сохранённый offset, отсутствие обычных дублей и конкуренция двух исполнителей, повторный явный `/start`, permanent send 403, transient send 429 с retry_after и восстановление, permanent polling 401 и исправление статуса.
- TDD: первый тест до реализации не собирался из-за отсутствия интерфейса бота. Регрессия polling401 до исправления воспроизводила ошибку `connected` вместо `error`, после исправления проходит.
- Frontend: `npm run typecheck` и `npm run build` — проходят.
- Playwright: `TEST_DATABASE_URL=... npm run test:e2e` — **6 passed**; `TEST_DATABASE_URL=... npx playwright test -c playwright.bot.config.js` — **2 passed**. Состояния подключения, ссылка и инструкция, перезагрузка, ошибка и повторная проверка подтверждены на desktop и phone; горизонтального переполнения нет.
- `docker build -t tracking:telegram-bot .` — проходит, собираются оба production binary и фронтенд. Отдельный Compose `tracking-bot-smoke` с фиктивной конфигурацией запускает API, PostgreSQL и bot; проверено повторное создание контейнеров с финальным образом. Без обязательной конфигурации `/bot` завершается с понятной ошибкой до запуска polling. Readiness — 200, закрытое состояние без сессии — 401, `/test-bot` и `/test-login` отсутствуют (404).
- Собственные временные контейнеры, сети и volume обоих Compose-проектов удалены после проверки. Ресурсы параллельной задачи не затрагивались.
- `git diff --check` — проходит. Двухосевое ревью и повторное ревью исправления завершены, [отчёт](../../../docs/reviews/05-connect-telegram-bot.md): Standards 0, Spec 0 оставшихся замечаний.
