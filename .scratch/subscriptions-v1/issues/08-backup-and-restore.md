# 08: Резервное копирование и восстановление

**What to build:** Владелец может восстановить приложение из ежедневной внешней копии базы, включая подписки, подключение бота и журнал доставки. Реализовать и проверить полный путь копирования и восстановления по согласованной спецификации.

**Blocked by:** 07 — Доставка напоминаний при сбоях.

**Status:** ready-for-agent

**User stories:** 34, 35.

- [x] Ежедневное копирование создаёт согласованную копию PostgreSQL и выгружает её во внешнее хранилище. Настройка назначения и реквизитов отделена от исходного кода и frontend-сборки.
- [x] Хранятся последние семь успешно полученных внешних копий. Сбой создания или выгрузки не удаляет последнюю исправную копию; политика хранения применяется после подтверждённого успеха.
- [x] Доступны время и результат последнего копирования; ошибка видна в эксплуатационном выводе, а секреты и финансовые данные не раскрываются.
- [x] Документированы подготовка, запуск и проверка восстановления в чистую базу, а также отдельное восстановление конфигурации и секретов. Допустимая потеря при исправном ежедневном копировании — последние сутки.
- [x] Реальная проверка копирования и восстановления в отдельную PostgreSQL подтверждает сохранность подписок, подключения, позиции обновлений и журнала доставки. Восстановление проверяется чтением через приложение и запуском фонового цикла с тестовым Telegram.
- [x] Фоновая отправка не включается вслепую после восстановления: описана проверка текущей дневной подборки. Учтено, что старая копия могла потерять подтверждение отправки и потому допустить повтор сообщения.
- [x] Инструменты копирования и проверки работают в согласованном контейнерном окружении. Без реальных реквизитов внешнего хранилища допускается контролируемое тестовое назначение; копирование на тот же production-сервер не считается выполнением требования внешней копии.
- [x] Записаны результаты проверок, оставшиеся параметры реального хранилища для задачи 09 и завершение задачи.

## Implementation

**Состояние реализации: завершена.** Проверено 16 октября 2026 года. `ready-for-agent`
сохранён как triage-метка. Зависимость 07 завершена до начала работы. Реализация:
`109e7e5`. Независимое двухосевое [ревью](../../../docs/reviews/08-backup-and-restore.md):
Standards — 0 замечаний; Spec — 0 замечаний.

Отдельный контейнер PostgreSQL 17 client / AWS CLI создаёт custom-format дамп
всей базы сразу при запуске, затем ежедневно в 02:00 UTC (05:00 Москвы).
S3 bucket/prefix, endpoint, регион и credentials задаются через `.env.backup`,
исключённый из Git и Docker build context. После выгрузки в staging архив
скачивается и проверяется по SHA-256; только затем публикуется окончательная
копия и удаляются объекты сверх семи. Сбой dump/upload/проверки не удаляет
исправные копии. Результат и UTC-время доступны через `status` и container logs;
подробные ошибки внешних утилит, DSN и содержимое базы не печатаются.

Команда `restore` скачивает выбранный объект, проверяет checksum, отвергает
занятую базу и восстанавливает в одной транзакции. Сама команда не запускает
workers. [Инструкция](../../../docs/backup-and-restore.md) описывает подготовку,
чистый Compose project, отдельное восстановление конфигурации и секретов,
проверку API и журнала текущего дня, а также включение отправителей по отдельности.
Возможная потеря подтверждения отправки и повтор сообщения явно описаны.

## Validation

- Границы TDD подтверждены владельцем в этой сессии: публичный CLI с S3 и настоящей
  PostgreSQL, API восстановленного приложения и workers с тестовым Telegram.
  Первый запуск CLI-проверки остановился на сборке из-за отсутствующего инструмента;
  сквозной тест затем
  выявил ошибку передачи URI через `PGDATABASE` (`stage=dump`). После перехода на
  `--dbname` обе проверки проходят.
- CLI: восемь реальных дампов с выгрузкой и скачиванием через Moto S3 оставляют
  ровно семь копий. Отсутствующая исходная база и недоступный bucket дают ошибки,
  сохраняя прежний набор и `last_success`. Проверяется безопасный вывод и статус.
- `TestBackupRestoresApplicationAndWorkers` с `-race`: отдельная PostgreSQL 17
  получает полную копию; через защищённый API читаются исходная точная сумма,
  название до изменения источника, архив и подключение. Polling получает
  сохранённый offset=2. Подтверждённый день не повторяется; неподтверждённая отправка
  соблюдает сохранённую задержку и затем доставляется один раз прежнему получателю.
  Повторное восстановление в занятую базу отвергается. Каждый прогон создаёт
  собственную чистую базу восстановления.
- Полный `./scripts/check.sh`: успешно — CLI/S3, JavaScript typecheck, Vite build,
  `go vet ./...`, весь `go test -race ./... -count=1` с PostgreSQL и **16 браузерных
  проверок** (12 основных + 4 подключения/доставки, desktop/phone). Первый прогон
  остановился перед браузером из-за старого `TestBrowserFixture` на порту 18080;
  после остановки этого тестового процесса полный прогон прошёл. Контейнеры,
  тестовый state volume и сеть удалены скриптом.
- `git diff --check`, `sh -n scripts/check.sh` и Python compilation проходят.
- После ревью финальный полный `./scripts/check.sh` на точном коммите реализации
  `109e7e5` также прошёл, включая восстановление и все 16 браузерных сценариев.

## Остаётся для задачи 09

Конкретный внешний provider/HTTPS endpoint, bucket/prefix, регион, credentials
с ограниченными правами, encryption/version lifecycle и удаление staging;
защищённая копия `.env`/`.env.backup`, мониторинг ошибок и возраста `last_success`;
проверка восстановления с настоящим назначением. Moto — контролируемое тестовое
назначение, а не внешняя production-копия. На production копии должны храниться
вне сервера; допустимая потеря — сутки при исправном ежедневном копировании.
