# Рядом — учёт регулярных расходов

Реализованы вход одного владельца через Telegram, сохраняемые сессии, добавление подписок и адаптивный список ближайших плановых платежей. Также реализованы редактирование, архив, итоги по валютам и ежедневная подборка с сохраняемыми повторами, защитой от параллельной отправки и видимой ошибкой подключения бота.

## Локальный запуск

Требуются Docker Engine и Compose v2 с поддержкой `--wait`.

1. `cp .env.example .env`
2. В `.env` задайте случайный URL-safe пароль PostgreSQL, числовой Telegram ID владельца, Client ID и Client Secret из BotFather → Login Widget. Не используйте username или bot token вместо Client Secret. Для подключения бота отдельно задайте `TELEGRAM_BOT_USERNAME` без `@` и `TELEGRAM_BOT_TOKEN` из BotFather.
3. В BotFather зарегистрируйте origin `http://localhost:8080` и callback `http://localhost:8080/api/auth/telegram/callback`. Если Telegram требует HTTPS для выбранного окружения, используйте HTTPS-домен с прокси и соответствующий `APP_ORIGIN`.
4. `cp .env.backup.example .env.backup && chmod 600 .env.backup`; для production заполните внешнее S3-хранилище по [инструкции backup/restore](docs/backup-and-restore.md).
5. `docker compose up --build -d`
6. Откройте `http://localhost:8080`. API и собранный React обслуживаются одним Go-процессом с одного origin.

`docker compose down` сохраняет базу в именованном volume. `down -v` удаляет данные. База не публикует порт в рабочем Compose. Приложение слушает только loopback хоста; HTTPS-прокси должен вести на `127.0.0.1:8080`. В HTTPS-окружении задайте HTTPS `APP_ORIGIN`: cookie автоматически получает Secure. Адрес не выводится из недоверенных forwarded-заголовков. Реальные секреты и домен нужны только для живого входа; автоматические тесты обходятся без них.

Конфигурация проверяется до начала обслуживания; STATIC_DIR должен содержать читаемый index.html собранного фронтенда. Origin не содержит путь или завершающий `/`. HTTP допускается только для localhost/127.0.0.1. `DATABASE_URL` задаётся Compose; для самостоятельного запуска нужен PostgreSQL DSN. `STATIC_DIR` по умолчанию `frontend/dist` относительно рабочего каталога, в образе `/web`. Случайные идентификаторы сессий не требуют отдельного ключа подписи: в PostgreSQL сохраняется SHA-256 от 256-битного токена. Сессия действует семь дней, запрос входа — десять минут. Старые истёкшие записи удаляются при начале нового входа.

Миграции применяются транзакционно при старте под advisory lock. Более новая версия схемы блокирует запуск. `/health/live` проверяет процесс, `/health/ready` — доступность базы и версию схемы; ответы не раскрывают конфигурацию. Отдельный процесс бота получает `/start` через long polling; ежедневную подборку обрабатывает отдельный процесс `/digest` ([устройство и ограничения](docs/daily-digest.md)).

## Проверки

На машине с Docker, Go 1.20+ и Node 22.12+ (или Node 24):

```sh
./scripts/check.sh
```

Скрипт поднимает отдельную настоящую PostgreSQL на loopback-порту 55432, выполняет проверку JavaScript через TypeScript `checkJs`, сборку, `go vet`, HTTP-тесты с race detector и браузерные сценарии Chromium для телефона и компьютера, затем удаляет тестовую базу. Требуется доступ к registry Go/npm и загрузке браузера. Не задавайте рабочую базу как `TEST_DATABASE_URL`.

Скрипт также проверяет CLI backup с тестовым S3 и восстанавливает внешнюю копию
в отдельную PostgreSQL на порту 55433. Проверки читают восстановленные данные
через API и запускают фоновые циклы с тестовым Telegram. Реальные реквизиты
хранилища не нужны; подробности — в [инструкции backup/restore](docs/backup-and-restore.md).

Для разработки и отдельных проверок:

```sh
docker compose -f compose.test.yaml up -d --wait
export TEST_DATABASE_URL='postgres://tracking:test-only@127.0.0.1:55432/tracking_test?sslmode=disable'
(cd backend && go test ./internal/app -run TestOwnerLoginSessionAndLogout -v)
(cd backend && go vet ./...)
(cd frontend && npm ci --ignore-scripts && npm run typecheck && npm run build)
(cd frontend && npx playwright install chromium && npm run test:e2e)
```

Без `TEST_DATABASE_URL` интеграционные тесты явно пропускаются; такой прогон не подтверждает вход и сохранение сессий. HTTP-тесты заменяют только транспорт внешнего Telegram и часы, используют настоящие RSA-подписи, JWKS, PKCE и PostgreSQL. Они проверяют чужой ID, повреждённую подпись, обязательные claims, issuer/audience/nonce, срок действия, повтор callback, CSRF, сохранение сессии при новом подключении и выход. Браузерный провайдер находится исключительно в `_test.go`; он не включается в рабочий бинарный файл. В production нет переменной или маршрута обхода авторизации.

Для будущих API-маршрутов добавляйте обработчики внутрь защищённой диспетчеризации `Server.ServeHTTP`. `GET /api/session` возвращает `owner.telegramId` (строка) и `csrfToken`. Изменяющие запросы должны отправлять заголовок `X-CSRF-Token`; Origin должен совпадать с `APP_ORIGIN`. Выход: `POST /api/logout`, ответ 204. Cookie — HttpOnly, SameSite=Lax, с ограниченным сроком; ответы API не кешируются. Telegram настроен на RS256 по умолчанию: другие алгоритмы намеренно отклоняются. Client Secret, access token и ID token не возвращаются клиенту и не журналируются.

## Git

Проект использует обычный Git-репозиторий в `.git`. История первоначальной реализации перенесена из временного `.git-storage`; стандартные команды `git status`, `git log` и `git commit` работают без дополнительных переменных.

## Подписки

Реализованы добавление и отдельные списки активных/архивных подписок. Форма и список работают на телефоне и компьютере; ошибки полей сохраняют ввод. Доступны изменение, архивация, итоги и ежедневная подборка ([устройство и ограничения](docs/daily-digest.md)).

Закрытые маршруты:

- `GET /api/meta` — `periodDays: [30,90,180,365]`, `currencies: [{code, fractionDigits}]` (RUB, USD, EUR, точность 2), `timezone: "Europe/Moscow"`, `today: "YYYY-MM-DD"` из серверных часов.
- `POST /api/subscriptions` — JSON с `name`, `amount` (десятичная строка с точкой), `currency`, `periodDays`, `nextPaymentDate`. Заголовок `X-CSRF-Token` берётся из сессии, Origin совпадает с origin приложения. Ответ 201 содержит сохранённую подписку.
- `GET /api/subscriptions?state=active` или `state=archived` — JSON-массив подписок. Обязательный `state` проверяется. Порядок: актуальная дата, название, ID.

Представление подписки: `id`, `name`, `amount`, `currency`, `periodDays`, `nextPaymentDate`, `archived`, `createdAt`, `updatedAt`. Суммы хранятся в PostgreSQL `numeric` и передаются строками; положительная сумма принимается без экспоненты, с точностью валюты и длиной до 100 символов. Даты — календарные, время создания/изменения — RFC 3339. Ошибки полей: HTTP 422, `{"error":{"code":"validation","message":"…","fields":{"amount":"…"}}}`; некорректный JSON — 400, неожиданная ошибка — 500 без внутренних подробностей.

Миграция 2 дополняет схему входа из задачи 01. Исходная следующая дата хранит график; чтение вычисляет актуальную дату, сохраняя целое число периодов. Архивные даты не меняются. Общая операция `ListSubscriptions(ctx, archived, now)` и модуль `internal/subscriptions` доступны последующим итогам и напоминаниям: их расчёт не требует предварительного открытия сайта. Сегодня определяется по Москве, независимо от зоны сервера и браузера. Это прогноз, без подтверждения фактических списаний.

Подключение бота, состояния и обработка ошибок: [docs/telegram-bot.md](docs/telegram-bot.md).
