# Резервное копирование и восстановление

Сервис `backup` запускается сразу и ежедневно в 02:00 UTC (05:00 Москвы).
При исправном ежедневном копировании допустима потеря последних суток изменений.
После пропуска запуска это окно увеличивается: контролируйте возраст `last_success`.
Единственный scheduler и ручные команды используют общий volume `backup-state`
с блокировкой. Не запускайте независимые scheduler с тем же bucket/prefix.

## Подготовка внешнего назначения

Скопируйте `.env.backup.example` в `.env.backup`, установите права 600.
Задайте существующий приватный S3 bucket, выделенный prefix с завершающим `/`,
регион, ключ и секрет. Для другого S3-провайдера задайте HTTPS endpoint.
Не записывайте реальные значения в Git, Dockerfile или frontend environment.
Файл исключён из Git и Docker build context. Реквизиты получает только backup.
Выдайте ListBucket только для prefix и GetObject/PutObject/DeleteObject для
объектов в нём; CopyObject требует чтение источника и запись назначения.
Нужны доступ наружу, TLS, корректное серверное время и место во временной
директории минимум для двух дампов. Шифрование at rest включите у провайдера.

Хранилище должно находиться **вне production-сервера**, под отдельной учётной
записью; локальный volume, соседняя папка и S3 на этом же сервере не подходят.
Автоматический тестовый Moto в Compose — контролируемое назначение для проверки
протокола, не production backup. HTTP разрешён только явным
`BACKUP_ALLOW_HTTP_TEST_ONLY=1`; в production эту переменную не задавайте.

Используется PostgreSQL 17 client из того же семейства образов, что и база.
[`pg_dump --format=custom`](https://www.postgresql.org/docs/17/app-pgdump.html)
снимает согласованный снимок всей базы при работающем приложении: подписки,
архив, сессии, подключение Telegram, позиция обновлений, журнал и сроки повторов.
Кластерные роли, конфигурация сервера и секреты окружения в дамп не входят.
Восстановление выполняется под заранее созданной ролью владельца без исходных ACL.

Дамп проверяется `pg_restore --list`, загружается в `staging/` с SHA-256 metadata,
скачивается и сравнивается с исходной суммой. Только затем атомарный S3 CopyObject
публикует окончательный `.dump` с той же metadata. Хранятся последние семь таких
копий; ротация выполняется только после подтверждённого успеха. Сбой dump/upload/
проверки не удаляет исправные копии. Сбой ротации виден как ошибка; временно может
остаться больше семи копий. Staging не учитывается; настройте lifecycle удаления
`<prefix>staging/` через несколько дней. Для versioned bucket lifecycle старых
версий согласуйте отдельно: CLI ограничивает семь текущих объектов.

```sh
docker compose up -d --build backup
docker compose run --rm --no-deps backup backup
docker compose run --rm --no-deps backup status
docker compose run --rm --no-deps backup list
docker compose logs --tail=20 backup
```

Пока daemon держит блокировку, разовая команда `backup` ответит `busy`.
Для внепланового снимка сначала `docker compose stop backup`, выполните команду
и снова `docker compose up -d backup` (при старте будет ещё один снимок).
`status` и `list` работают параллельно. Статус содержит UTC-время начала/конца,
`result`, безопасный `stage`, время `last_success` и ключ копии. `running`,
оставшийся после аварии, и отсутствие свежего успеха требуют внимания.
JSON пишется атомарно в volume; тот же результат поступает в container logs.
Однократный сбой даёт ненулевой exit code; daemon пишет ошибку и продолжает
ежедневное расписание. Настройте внешний мониторинг ошибок и возраста успеха
(больше 26 часов); локальный статус сам по себе не является оповещением.
stderr утилит скрыт, чтобы не раскрыть DSN, ключи, SQL и финансовые данные.

## Восстановление в чистую PostgreSQL

1. Остановите `bot`, `digest` и `backup` на старом сервере, затем `app`.
   Сохраните исходную базу/volume до проверки результата. Не используйте `down -v`.
2. На чистом окружении получите тот же проверенный commit приложения и Docker
   Compose. Из отдельного защищённого места восстановите `.env` и `.env.backup`,
   домен/HTTPS-прокси, Telegram ID, bot username/token и Login Client ID/Secret,
   доступ к S3. При компрометации замените секреты и проверьте настройки BotFather.
   Ни база, ни внешний дамп не заменяют эту отдельную копию конфигурации.
3. Создайте **новый Compose project**, например `tracking-recovery`, чтобы
   PostgreSQL получил новый volume, а исходные данные остались доступны.
   Поднимайте пока только `db`; приложение и отправители ещё не запускайте.

```sh
docker compose -p tracking-recovery up -d --wait db
docker compose -p tracking-recovery run --rm --no-deps backup list
```

4. Выберите конкретный ключ из списка (последний — самый новый). Через защищённое
   окружение задайте `RESTORE_DATABASE_URL` новой базы: host `db`, database/user
   `tracking`, пароль из восстановленного `.env`. Не печатайте DSN и не включайте
   shell tracing. Переменная должна быть экспортирована; Compose передаст её по имени.

```sh
docker compose -p tracking-recovery run --rm --no-deps -e RESTORE_DATABASE_URL backup restore 'tracking/production/KEY.dump'
```

Скачивание проверяет SHA-256. В целевой базе не должно быть пользовательских
relations; занятая база отвергается. [`pg_restore`](https://www.postgresql.org/docs/17/app-pgrestore.html)
использует одну транзакцию с остановкой при ошибке, без `--clean`: неуспех не
оставляет частично восстановленную базу. Команда не запускает приложение или workers.
Глобальные роли создаются PostgreSQL image из `.env`, ACL из дампа не применяются.

5. Поднимите **только API**: `docker compose -p tracking-recovery up -d --build app`.
   Проверьте `/health/ready`, вход владельца, активные и архивные подписки, точные
   суммы и даты, состояние подключения бота. Сессии из копии сохраняются, пока
   не истекли; после компрометации отзовите их отдельно. Перед включением workers
   сравните служебный журнал с текущим московским днём и историей настоящего чата:

```sh
docker compose -p tracking-recovery exec db psql -U tracking -d tracking -c "SELECT business_date,status,attempts,last_result,next_attempt_at FROM daily_digests ORDER BY business_date DESC LIMIT 7"
docker compose -p tracking-recovery exec db psql -U tracking -d tracking -c "SELECT status,next_update_id FROM telegram_connections"
```

Не выводите `message_text`, recipient, токены или подписки в общие логи.
`sent` и `empty` не отправляются повторно; `pending` текущего дня после 10:00
может продолжиться с сохранённым текстом и задержкой. Отсутствие строки допускает
новую подборку. Прошлые дни worker не догоняет.

6. **Не включайте фоновую отправку вслепую.** Старая копия могла потерять
   подтверждение уже доставленного сообщения, а также более новую позицию
   обновлений `/start`. Возможны повтор подборки и проверочного сообщения.
   Если сегодняшний чат и журнал расходятся или исход неизвестен, оставьте
   `digest` остановленным до следующего московского дня; затем запускайте после
   проверки актуальных подписок. Либо владелец явно принимает возможный дубль
   сегодня и разрешает продолжить. Не помечайте неизвестную доставку как успешную.
   Позицию polling проверьте до запуска `bot`, учитывая возможный повтор `/start`.
7. После проверки запустите по отдельности `bot`, `digest`, затем `backup` через
   `docker compose -p tracking-recovery up -d <service>`. Проверьте состояние
   подключения, отсутствие обычных дублей и свежий успешный внешний снимок.
   Старые отправители должны оставаться остановленными. Сохраните время и итог
   восстановления без финансовых данных и секретов.

## Воспроизводимая проверка

`./scripts/check.sh` поднимает PostgreSQL 17 для источника и отдельный PostgreSQL
для восстановления плюс Moto S3. CLI-тест делает восемь выгрузок, проверяет семь
копий и сохранение последней при сбое создания/выгрузки. Go-сценарий
`TestBackupRestoresApplicationAndWorkers` создаёт данные через API и тестовый
Telegram, выгружает всю базу, меняет источник и восстанавливает внешнюю копию
в чистый контейнер. Через API проверяет точную сумму, архив, подключение и снимок
до изменения, через polling — сохранённый offset, через digest — отсутствие
повтора подтверждённого дня и продолжение неподтверждённого с прежней задержкой.
Повтор restore в занятую базу отвергается. Telegram целиком тестовый, production
credentials не нужны. Контейнеры и тестовые volumes удаляются после прогона.

Для задачи 09 остаются: реальный внешний provider/endpoint, bucket/prefix,
регион, отдельные credentials и права, encryption/version lifecycle, размещение
защищённой копии конфигурации, мониторинг и пробное восстановление с настоящим
назначением. Тестовое S3 на машине разработки не подтверждает внешний production
backup. Проверку восстановления повторяйте после изменения схемы или инструментов.
