# Ежедневная подборка плановых платежей

Отдельный процесс `/digest` запускается сервисом `digest` в Docker Compose. При старте и затем раз в минуту он проверяет текущую дату в Europe/Moscow. До 10:00 сообщения нет; первая проверка начиная с 10:00 формирует текущую подборку. Открывать сайт для переноса прошедших дат не требуется: worker использует тот же прогноз фиксированных периодов, что и API.

Процессу нужны `DATABASE_URL`, `OWNER_TELEGRAM_ID`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_BOT_TOKEN` и `APP_ORIGIN`. Origin проверяется так же, как у API: HTTPS, без пути, query, fragment и credentials; локально допускается HTTP loopback. Дополнительная граница длины origin — 2048 UTF-16 единиц, чтобы ссылка помещалась в компактное сообщение. Login Client Secret процессу не нужен. Ошибки отправки журналируются без токена, URL запроса и финансовых данных.

Только подтверждённо подключённый через `/start` бот получает подборку. Активные подписки с ближайшей датой сегодня или через три дня попадают в соответствующий раздел. Сообщение содержит названия, точные суммы, исходные валюты и даты. Telegram получает plain text без `parse_mode`: HTML и Markdown в названии остаются буквальным текстом. Если сообщение превышает 4096 UTF-16 единиц, отправляется одна компактная подборка с общим количеством платежей, количеством в непустых разделах и ссылкой на полный список. Ссылка равна `APP_ORIGIN/`, требует обычного входа и не содержит финансовых данных или секретов.

Миграция 3 создаёт `daily_digests`: одна запись на московскую дату с получателем, зафиксированным текстом, временем создания и состоянием `pending`, `empty` или `sent`. Текст сохраняется отдельным commit до первого обращения к Telegram. Успех фиксируется только после подтверждения Telegram. Обычный перезапуск повторяет только неподтверждённую попытку с сохранённым содержимым. Пустой день также остаётся обработанным. Изменения подписок сразу видны на сайте, но не создают ещё одно сообщение уже обработанного дня. Проверочное сообщение `/start` существует отдельно от этого журнала. Пока получатель не подключён, день не фиксируется: подключение до конца дня позволяет сформировать актуальную подборку.

Публичная граница проверки: `app.NewDigestWorker(db, config, telegram).Cycle(ctx, now)`. Каждый цикл получает заданное время, использует настоящую PostgreSQL и внешний Telegram-адаптер. Тесты `TestDigest*` создают изолированные схемы, сохраняют подписки через защищённый HTTP API и наблюдают исходящие сообщения через подменный HTTP transport Telegram. Новое подключение к базе и новый worker между циклами проверяют сохранность после обычного перезапуска.

```sh
cd backend
TEST_DATABASE_URL='postgres://tracking:test-only@127.0.0.1:55432/tracking_test?sslmode=disable' go test ./internal/app -run '^TestDigest' -race -count=1
```

Миграция 4 добавляет число неудачных попыток `attempts` и сохранённый срок `next_attempt_at`. Сетевой сбой, таймаут с неизвестным результатом, HTTP 429 и временный отказ повторяются с тем же текстом. Задержка после получения ошибки: 1, 2, 4, 8, 16, 32 минуты, затем не больше часа; если Telegram просит `retry_after` дольше, учитывается его срок. Проверка раз в минуту может отправить позже этого срока, но не раньше. Обычный перезапуск не обнуляет задержку. После аварии до фиксации результата срок последней попытки может быть утрачен: следующий цикл возобновляет неподтверждённую отправку.

Уникальная дата защищает создание снимка. Транзакционный `FOR UPDATE SKIP LOCKED` атомарно захватывает готовую подборку и удерживает строку до фиксации результата отправки. Другой исполнитель пропускает занятую строку; зависшей аренды нет. При потере соединения с PostgreSQL или завершении процесса транзакция откатывается и блокировка освобождается. Цикл процесса ограничен 45 секундами, обращение к Telegram — 35 секундами и оставшимся временем до московской полуночи. Контекст отправки отменяется на границе дня; уже принятый Telegram запрос отменить нельзя. Старые `pending` сохраняются как журнал, но никогда не выбираются для отправки на следующую дату. После многодневного простоя используется общий прогноз графика на текущую дату, без создания подборок за прошлые дни.

Постоянный отказ (400, 401, 403, в том числе блокировка бота) сохраняет `error` в подключении и прекращает отправки, пока владелец не восстановит связь через `/start`. API `/api/telegram/connection` и русский интерфейс показывают «Бот недоступен»; управление подписками продолжает работать. Успешный проверочный `/start` возвращает `connected`, и готовая неподтверждённая подборка текущего дня может продолжиться с прежним текстом. Миграция Telegram 2 добавляет ревизию проверки подключения: поздний отказ старой отправки не перезаписывает более новую проверку `/start`.

Между принятием сообщения Telegram и сохранением успеха возможен редкий дубль, в том числе после таймаута или потери соединения с базой. У `sendMessage` не предполагается документированный ключ идемпотентности; строго однократная доставка не обещается. Восстановление старой резервной копии также может утратить подтверждение отправки. Живая проверка с настоящим ботом и доменом относится к настройке развёртывания.
