# Подключение Telegram-бота

Фоновый процесс `/bot` получает `/start` через long polling и отправляет проверочное сообщение. Основной путь ежедневной подборки реализован отдельным процессом `/digest`: [устройство и ограничения](daily-digest.md). Повторы, параллельные исполнители и восстановление описаны там же.

В `.env` задайте `TELEGRAM_BOT_USERNAME` (без `@`) и `TELEGRAM_BOT_TOKEN` из BotFather, отдельно от Client ID/Client Secret для входа. `OWNER_TELEGRAM_ID` — положительный числовой ID владельца. API использует только username для ссылки; токен доступен только фоновому процессу. Конфигурация проверяется до запуска. Telegram Bot API использует фиксированный HTTPS-адрес; переменных для обхода авторизации или замены Telegram в production нет.

`docker compose up --build -d` запускает API, PostgreSQL и bot. Polling требует отсутствия webhook у этого бота: удалите старый webhook перед запуском, если он был настроен. Не используйте этого же бота в другом приложении с getUpdates. Откройте приложение, войдите, нажмите «Открыть бота», отправьте `/start` в личном чате и дождитесь проверочного сообщения. Нажмите «Проверить подключение» или вернитесь в приложение: состояние обновляется при возвращении и каждые 10 секунд на видимой странице.

`GET /api/telegram/connection` защищён общей сессией и возвращает `status` и `botUrl`. Состояния: `disconnected` — `/start` ещё не принят; `checking` — проверочная отправка ожидает повтора после временного сбоя; `connected` — Telegram подтвердил отправку; `error` — постоянный отказ проверки или доставки ежедневной подборки. Последнее состояние не является непрерывным мониторингом Telegram. При блокировке разблокируйте бота и отправьте новый `/start`. Вход на сайт не меняет подключение. Ошибка проверки подключения не блокирует другие функции сайта.

Бот проверяет числовой ID отправителя и private-тип чата, сохраняет именно chat_id. Чужие и групповые обновления пропускаются без ответа. Позиция обновлений, chat_id и состояние хранятся в PostgreSQL. Миграция Telegram использует собственную версионируемую таблицу `telegram_schema_migrations` и общий транзакционный advisory lock запуска. Readiness проверяет обе версии схемы. Миграции подписок и Telegram независимы.

Один цикл обрабатывает не больше одного обновления. Блокировка строки подключения сериализует получение, отправку и запись позиции между исполнителями. Подтверждённый результат и позиция фиксируются одной транзакцией; обычный перезапуск не повторяет сообщение. Если процесс упал между принятием сообщения Telegram и commit, возможен согласованный редкий дубль. Временная ошибка сохраняет `checking` без продвижения позиции; повтор учитывает `retry_after`, минимальная задержка — 5 секунд. Постоянный отказ проверочной отправки сохраняет `error` и продвигает позицию: новая проверка требует явного `/start`. Постоянный отказ самого polling сохраняет `error` и повторяется не чаще раза в минуту. Проверьте токен и конфигурацию, перезапустите процесс, затем отправьте новый `/start`. Ошибки журналируются без URL, токенов и ответов Telegram.

Проверки: `./scripts/check.sh` включает PostgreSQL, Go race/vet, JavaScript typecheck/build и браузерные сценарии. Отдельно: `TEST_DATABASE_URL=... go test ./internal/app -run '^TestBot' -race -count=1` из backend; `TEST_DATABASE_URL=... npx playwright test -c playwright.bot.config.js` из frontend после сборки. Браузерный сервер порта 18081 и его управляющие маршруты существуют исключительно в `_test.go`; каждый браузер получает отдельного тестового владельца.

Живая проверка с настоящим ботом и доменом выполняется при развёртывании (задача 09). Протокол проверен по [официальному Telegram Bot API](https://core.telegram.org/bots/api#getupdates), включая long polling, offset, sendMessage и retry_after.
